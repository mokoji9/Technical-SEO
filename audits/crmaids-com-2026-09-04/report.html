Critical Crawlability Moderate · hosting / plugin config

1. The two "Pages" sitemaps return a 500 timeout instead of XML

The sitemap index lists seven sub-sitemaps. Five load in about a second. The two that don't, page-sitemap1.xml and page-sitemap2.xml, are the WordPress Pages sitemaps, which normally carry the core service and location pages rather than blog posts. They are also the most recently updated entries in the index (3 Sep 2026, the day before this audit).

Tested six times across two audit passes and a re-check while preparing this report, with curl (default and Googlebot user-agents) and a real browser. Every attempt hung until the server gave up. In the browser, the page rendered LiteSpeed's own error: "500 Internal Server Error, Request Timeout."

HTTP 200 | bytes 29538 | 1.371s

Why it matters: Google reads sitemaps to discover new and changed URLs quickly. With these two files unreadable, new or edited service pages rely on being found through internal links alone, and Search Console will report the sitemap as failing. This is a server-side bug, most likely the sitemap generator timing out while building these entries or a caching plugin interfering with the dynamic XML endpoint. Editing the sitemap itself won't fix it.

Before changing anything: ask your host to pull the server error log for a request to page-sitemap1.xml. The log entry will show exactly what timed out. Then confirm in Google Search Console under Sitemaps that the index currently shows an error for these two files.
How to fix it, step by step WordPress admin + hosting panel
  1. See what those two sitemaps are trying to list. In WordPress go to Pages → All Pages and sort by date. An unusually large number of pages, or a few very heavy Divi layouts, can make the generator time out while building their entries.
  2. Exclude sitemap URLs from WP Rocket. The site runs WP Rocket 3.21.3. Go to WP Rocket → Advanced Rules → Never Cache URLs and add /(.*)sitemap(.*).xml. Also make sure sitemaps are not covered by Remove Unused CSS or Delay JavaScript. If LiteSpeed Cache is also installed, exclude *sitemap*.xml there too.
  3. Ask your host to raise the limits. Request a higher PHP max_execution_time and a longer LiteSpeed connection timeout for the site. On Hostinger this is under Advanced → PHP Configuration. If the generator only needs a few more seconds, this alone can fix it.
  4. Regenerate the sitemaps. Rank Math: Rank Math → Sitemap Settings, toggle sitemaps off and on. Yoast: SEO → General → Features → XML sitemaps off and on. Then clear the WP Rocket cache.
  5. Pull the server error log. In the hosting panel open Error Logs, request https://crmaids.com/page-sitemap1.xml in a browser, and read the newest entry. It names the plugin or query that hung.
  6. If it still hangs, ask the host whether a memory or CPU limit is being hit on that URL. Shared plans sometimes throttle long processes, which looks identical from outside.
Done when: the curl command above returns HTTP 200 in under 5 seconds with real XML, and Google Search Console → Sitemaps shows "Success" with a URL count for both files.

2. Homepage weighs ~8 MB; a batch of uncompressed JPEGs drives LCP to 5–6 seconds

Lighthouse Performance scored 54 to 56 out of 100 across three runs, with Largest Contentful Paint between 5.1 and 6.0 seconds. Google's "good" threshold is 2.5 seconds.

The cause is specific. Several photos uploaded in August 2026 (IMG_5057-scaled.jpg, IMG_2638-scaled.jpeg, 83ad71b4…-scaled.jpg, and others from the same batch) are each around 620 to 640 KB and load as plain JPEGs, even though the rest of the site already serves WebP. Those few files alone account for roughly 1.9 MB of the page.

Why it matters: LCP is a Core Web Vitals ranking signal, and on mobile connections an 8 MB homepage is slow enough that visitors leave before the first screen finishes painting. Converting this batch to WebP and adding explicit width and height attributes fixes both this and most of the layout shift in finding 4.

How to fix it, step by step Media Library
  1. Find the August batch. In Media → Library, filter to August 2026 and list view. Sort by file size if your media plugin allows it. The offenders are the -scaled.jpg and -scaled.jpeg files around 620 to 640 KB.
  2. Compress and convert them to WebP. For a handful of files, drop each into Squoosh, choose WebP at quality 75 to 80, and resize to the largest width the layout actually displays. Aim for under 150 KB each. For bulk, use ShortPixel or Imagify and run a bulk optimization on the August uploads only.
  3. Replace the files in place. Use "Replace Media" (Enable Media Replace plugin) or re-upload and swap the images in the Divi modules, so existing URLs keep working.
  4. Check width and height are present. WP Rocket's "Add missing image dimensions" is already on, but these images still shift. Open the homepage source and confirm each of these <img> tags has width and height. Where missing, set them in the Divi image module.
  5. Keep the hero eager, lazy-load the rest. The first image visitors see should not be lazy-loaded. Everything below the fold should be.
  6. Clear the cache in WP Rocket and re-test.
Done when: PageSpeed Insights no longer lists "Serve images in next-gen formats" or "Efficiently encode images", LCP is under 2.5 seconds, and total page weight in the browser Network tab is under about 3 MB.

3. Eight render-blocking resources on the homepage

Lighthouse flagged eight scripts and stylesheets that the browser must download and run before it can paint anything. WP Rocket is installed and already minifying, so the remaining blockers are likely theme and third-party scripts that are excluded from its deferral rules.

Why it matters: each blocking resource delays first paint, stacking on top of the image weight above. Deferring non-critical scripts is usually a settings change in WP Rocket rather than code work.

How to fix it, step by step WP Rocket settings
  1. Get the list. Run the homepage through PageSpeed Insights and open "Eliminate render-blocking resources". Note the eight files. They will be a mix of theme CSS, plugin scripts, and third-party tags.
  2. Defer JavaScript. In WP Rocket → File Optimization, turn on Load JavaScript deferred and Delay JavaScript execution. Delay holds third-party scripts until the visitor interacts, which covers most of finding 10 as well.
  3. Optimize CSS delivery. In the same screen, Remove Unused CSS is already on. Confirm it has finished processing for the homepage (it shows a status) and that Minify CSS is enabled.
  4. Add exclusions for anything that breaks. Reload the homepage and test the menu, booking form, and any sliders. If something stops working, add that script to the exclusion box under Delay JavaScript rather than turning the feature off.
  5. Move hard-coded tags into Tag Manager. Any pixel pasted directly into the theme header should be managed from Google Tag Manager instead, so it can load after first paint (see finding 10).
Done when: the render-blocking warning in PageSpeed Insights is gone or down to one or two files, and the site still works end to end, including the booking form.

4. Cumulative Layout Shift is 0.178

Consistent across every run. Google's "good" threshold is 0.1, so this sits in the "needs improvement" band, not yet "poor". Content jumps as the oversized images load without reserved space.

Why it matters: layout shift is the third Core Web Vital. Giving the images from finding 2 explicit dimensions typically brings this under 0.1 without separate work.

How to fix it, step by step After finding 2
  1. Finish finding 2 first and re-run PageSpeed Insights. Most of the shift comes from images loading without reserved space.
  2. Find whatever still shifts. In Chrome DevTools open the Performance panel, record a page load, and look at the "Layout Shifts" track. It highlights the exact elements that moved. Embedded widgets (Elfsight reviews, UserWay, LeadConnector chat) are the usual remaining causes.
  3. Reserve space for embeds. Give each widget's container a fixed min-height in the Divi module's Advanced → Custom CSS so the page doesn't jump when it loads.
  4. Check web fonts. If text visibly reflows when fonts arrive, WP Rocket's font preloading is already on. Confirm the fonts it preloads match the ones the theme actually uses.
Done when: CLS reads 0.1 or lower on three consecutive PageSpeed Insights runs.

Medium Mobile Quick win

5. The viewport tag blocks pinch-to-zoom

The homepage viewport tag sets maximum-scale=1.0 and user-scalable=0. Visitors on phones cannot zoom to read small text, which fails WCAG 1.4.4 and is one of the items holding Accessibility at 89 instead of 100.

curl -s https://crmaids.com/ | grep -o '<meta name="viewport"[^>]*>'
<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=0" />

Why it matters: Google's mobile-usability signals penalize disabled zoom, and it excludes visitors with low vision. The fix is deleting the last two values from one line.

How to fix it, step by step Theme header
  1. Find where the tag is set. Divi normally outputs a correct viewport tag, so something overrides it. Check, in order: Divi → Theme Options → Integration (the "Add code to the head" box), the child theme's header.php, and any "mobile" or "accessibility" plugin settings. Search each for user-scalable.
  2. Replace the tag with the standard form: 
    <meta name="viewport" content="width=device-width, initial-scale=1">
    Remove maximum-scale=1.0 and user-scalable=0. Nothing else changes.
  3. Clear the WP Rocket cache so the new header is served.
Done when: viewing the homepage source shows the new tag, pinch-zoom works on a phone, and the Lighthouse Accessibility audit no longer flags "user-scalable".

Low Crawlability Quick win

6. robots.txt carries a stale rule block from a different app

The file has two separate User-agent: * groups. The first disallows paths such as /admin/, /provider/, /qbconnect/, /live-reviews/, /sent_emails/, and /*.php, which look like leftovers from a non-WordPress system. The second is a normal WordPress block with Allow: /. Most crawlers merge same-agent groups correctly, so nothing is actively broken today.

curl -s https://crmaids.com/robots.txt
User-agent: * Disallow: /admin/ Disallow: /provider/ Disallow: /qbconnect/ Disallow: /images/ Disallow: /*.php … 12 more legacy rules … User-agent: * Allow: / Disallow: /wp-admin/ Sitemap: https://crmaids.com/sitemap_index.xml

Why it matters: stale rules make future edits risky, since someone could reintroduce a real block without noticing. Also confirm that Disallow: /images/ is intentional. Actual photos are served from /wp-content/uploads/, so it doesn't currently affect Google Images, but it's a trap waiting to spring.

How to fix it, step by step SEO plugin or site root
  1. Find where robots.txt lives. If a physical robots.txt file exists in the site root (check via the hosting file manager), edit that. Otherwise it is generated by the SEO plugin: Rank Math under General Settings → Edit robots.txt, Yoast under Tools → File editor.
  2. Merge the two blocks into one. Delete the first legacy User-agent: * group entirely. Keep the WordPress group. If any legacy path still exists on the server and should stay private, move that single line into the kept group.
  3. Decide on /images/. Photos are served from /wp-content/uploads/, so this rule currently does nothing. Remove it unless there is a real /images/ folder you want hidden.
  4. Keep the Sitemap line at the bottom pointing at https://crmaids.com/sitemap_index.xml.
  5. Test before saving. In Google Search Console open Settings → robots.txt and confirm it parses without warnings after the change.
Done when: curl https://crmaids.com/robots.txt shows a single User-agent: * group, and URL Inspection on a service page reports "Crawl allowed: Yes".

7. /contact redirects to /contact/

A trailing-slash normalization 301. Harmless on its own, but any internal link pointing at the no-slash version costs an extra hop for every crawl and click.

Fix: update internal links to point directly at the canonical /contact/. No dedicated guide needed.

How to fix it, step by step Menus and content
  1. Check the menus first. In Appearance → Menus and the Divi global header, open the Contact item and make sure its URL ends with a slash: https://crmaids.com/contact/.
  2. Search the content. Install "Better Search Replace", run a dry run for crmaids.com/contact" (with the closing quote, so it only matches the no-slash form) and review the hits.
  3. Replace with crmaids.com/contact/" and clear the cache.
Done when: a site crawl (Screaming Frog or similar) shows no internal links returning a 301 to /contact/.

8. Three duplicate generator tags and a duplicated site-data tag

WordPress, Site Kit by Google, and WP Rocket each inject their own <meta name="generator"> tag, and ti-site-data appears twice. The on-page scanner flags these as duplicate meta tags.

curl -s https://crmaids.com/ | grep -o '<meta name="generator"[^>]*>'
<meta name="generator" content="WordPress 7.0.4" /> <meta name="generator" content="Site Kit by Google 1.180.0" /> <meta name="generator" content="WP Rocket 3.21.3" … />

Why it matters: technically invalid HTML, but it has no ranking effect. Cosmetic cleanup only, and it also stops advertising exact plugin versions publicly.

How to fix it, step by step Child theme functions.php
  1. Remove the WordPress tag. Add this line to the child theme's functions.php (or a code-snippets plugin): 
    remove_action( 'wp_head', 'wp_generator' );
  2. Remove the plugin tags. Site Kit and WP Rocket each add their own. Both plugins document a filter for turning it off. Search each plugin's support docs for "meta generator" and add the one-line filter they give, or ask their support.
  3. Find the duplicated ti-site-data tag. It comes from a theme or plugin, most likely a reviews or testimonials widget. Deactivate plugins one at a time on a staging copy until the duplicate disappears, then report it to that plugin's author.
Done when: viewing the homepage source shows at most one generator tag and one ti-site-data tag.

9. No LocalBusiness or Organization schema on the homepage

The homepage already has well-formed FAQPage, Service, and WebSite schema with a SearchAction, and address and geo data nested inside. What's missing is an explicit LocalBusiness entity carrying the business name, address, phone, and hours as a first-class object.

Why it matters: for a local cleaning service this is the schema type Google uses for local pack and rich-result features such as business details in search. Not a defect, but the best-return addition available.

How to fix it, step by step SEO plugin schema settings
  1. Try the plugin first. Rank Math: Titles & Meta → Local SEO, set the site to represent an Organization, choose business type LocalBusiness, and fill in name, address, phone, opening hours, and logo. Yoast needs the Local SEO add-on for the same screen. This is safer than hand-coding because the plugin keeps it valid.
  2. If hand-coding, add one JSON-LD block to the homepage <head> via Divi → Theme Options → Integration, filling in the real details: 
    <script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "LocalBusiness",
  "name": "CR Maids",
  "url": "https://crmaids.com/",
  "image": "https://crmaids.com/wp-content/uploads/2025/11/main-logo-e1763962917467.webp",
  "telephone": "REAL PHONE NUMBER",
  "address": { "@type": "PostalAddress", "streetAddress": "…", "addressLocality": "…", "addressRegion": "…", "postalCode": "…", "addressCountry": "US" },
  "openingHoursSpecification": [ { "@type": "OpeningHoursSpecification", "dayOfWeek": ["Monday","Tuesday","Wednesday","Thursday","Friday"], "opens": "08:00", "closes": "18:00" } ],
  "areaServed": "…"
}
</script>
  3. Match the page. Every value must appear somewhere visible on the site. Google treats markup that doesn't match visible content as spam.
  4. Reuse the existing address and geo data. The homepage already carries PostalAddress and GeoCoordinates nested in other schema. Copy those values so the two agree.
Done when: the Rich Results Test detects LocalBusiness with no errors, and the existing FAQPage, Service, and WebSite types are still detected alongside it.

10. Heavy third-party script footprint

The homepage loads Google Tag Manager, Facebook Pixel, Microsoft UET, Google Ads and DoubleClick, Microsoft Clarity, an Elfsight widget, GoHighLevel LeadConnector, and the UserWay accessibility widget. Each adds network overhead on top of the image weight.

Why it matters: worth an audit of which of these are still in use, then loading the non-critical ones after first paint using Tag Manager's trigger delays. Fold this into the performance work in findings 2 and 3 rather than treating it separately.

How to fix it, step by step Google Tag Manager + WP Rocket
  1. Make an inventory. List the eight services above and, for each, write down whether it is still used and who owns it. Anything nobody claims gets removed.
  2. Bring everything under Tag Manager. If any pixel is pasted directly into the theme or a plugin, recreate it as a tag in the existing GTM container and delete the hard-coded copy. One container, one place to manage loading.
  3. Delay the non-essential tags. In GTM, change the trigger for Clarity, Bing UET, Facebook Pixel, and the Elfsight widget from "All Pages" to Window Loaded, or a Timer trigger of 3 to 5 seconds. Keep GTM itself and Google Ads conversion tags on page view if conversions depend on them.
  4. Let WP Rocket delay the rest. With Delay JavaScript execution on (finding 3), UserWay and the LeadConnector chat widget load after the first interaction instead of blocking the first paint.
Done when: the "Reduce the impact of third-party code" entry in PageSpeed Insights drops below about 500 ms, and Total Blocking Time improves alongside it.

What's already working

No action needed here. Worth knowing what not to touch.

  • ✓Security and HTTPS. HTTP forces HTTPS (301), www canonicalizes to the apex (301), HSTS with preload and a one-year max-age, plus CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy headers. Identical on both passes.
  • ✓Indexability basics. Self-referencing canonical, meta robots set to index, follow with sensible snippet directives, single canonical domain enforced.
  • ✓Lighthouse SEO 100/100 on the homepage, consistent across all runs.
  • ✓Five of seven sitemaps. The index, all four post sitemaps (200 URLs), and the local sitemap load correctly and are referenced from robots.txt. A sampled blog URL returns 200.
  • ✓Structured data present. FAQPage, Service, and WebSite with SearchAction, all well-formed.
  • ✓Real 404s. A non-existent URL returns a genuine 404, not a soft 404.
  • ✓No bot blocking or cloaking. A spoofed Googlebot user-agent gets the same 200 and the same content as a normal browser.
  • ✓Alt text on sampled images is descriptive. The scanner flagged a site-wide missing-alt signal worth a fuller image-by-image pass, but this isn't a wholesale failure.

Recommended order of attack

  1. Fix the two timing-out sitemaps (#1). The only confirmed critical bug, reproduced identically on every attempt. Have your host check the server error log for the exact timeout cause, then verify in Search Console under Sitemaps.
  2. Compress the August photo batch and clear render-blocking scripts (#2 and #3 together). Convert the oversized JPEGs to WebP, add width and height, then defer non-critical scripts. This moves the Performance score meaningfully and pulls CLS (#4) down as a side effect.
  3. Re-enable pinch-zoom (#5). One-line change to the viewport tag. Immediate accessibility and mobile-usability win.
  4. Batch the cleanup items (#6, #7, #8). Consolidate robots.txt, fix internal links to /contact/, drop duplicate generator tags. None is urgent on its own.
  5. Add LocalBusiness schema (#9). Good return for a local service business's local-pack visibility. Not urgent.
  6. Audit third-party scripts (#10). Fold into the performance work in step 2 rather than doing it separately.

Methodology: DataForSEO OnPage and Lighthouse APIs (three homepage runs), live browser checks, curl for status codes, headers, redirect chains, and bot-versus-browser user-agent comparison, and direct fetches of robots.txt and every sitemap.
